# 助手需要的数据：正式协议前的对齐材料

本文说明 App 侧助手（本地规则助手 + 可选在线助手）**需要什么数据、不需要什么数据**，用于和硬件组对齐正式事件协议。**这不是协议本身** —— 协议以 `protocol/ble-gatt.md` 和 `protocol/data-format.md` 为准。

## 现状：助手看不到真实设备数据

```text
ESP32（Arduino 原型）──BLE──▶ 原型时间文本库 ──✗──▶ 助手
正式事件帧（未冻结）  ──BLE──▶ 正式记录库 ──────▶ RecordSummary ──▶ 助手
```

助手的输入是 `AssistantContext`，它由 `RecordSummary` 生成，而 `RecordSummary` **只统计正式记录**。原型时间文本存在独立数据库，不进入摘要 —— 这是刻意设计，避免把"格式未定的时间文本"当作使用动作。

**结论：正式事件帧落地之前，原型时间文本不能用于真实事件统计。** 0.3.2 起已移除演示数据；没有完整设备事件时显示空摘要，本地仍能回答 App 用法，在线模式仍可回答一般问题。让助手解释实际使用记录，需要先完成正式事件解码入库。

## 助手需要的字段（当前已实现，不需要协议新增）

| 字段 | 来源 | 说明 |
|---|---|---|
| `total_count` | 记录条数 | 含时间未知与未来时间的记录 |
| `today_count` / `last_7_days_count` | 按本地日历日聚合 | 只统计 `event_type=1` 的使用动作 |
| `invalid_event_count` | `event_type=2` | 疑似无效事件 |
| `unknown_time_count` | `timestamp=0` | 无法计入按日统计 |
| `future_time_count` | 时间晚于当前时间 | 已排除在按日统计之外 |
| `daily_counts` | 近 7 天逐日次数 | 恒 7 项，之和必须等于 `last_7_days_count` |
| `last_sync_at` | 同步完成时刻 | 完整设备事件同步成功后写入 |

这些**全部能从现有 20 字节记录格式推导出来**，不需要为助手新增协议字段。

## 助手不需要的（隐私边界）

- 原始时间戳序列、设备标识（MAC 等）、单条记录明细 —— 一律不上传；
- 历史对话 —— **默认不发送**；「带上本轮对话」开启后，仅直连用户自己的模型时才发送本轮更早的问答（仍不发原始记录与设备标识）；
- 任何密钥、令牌或账号。

在线模式下用户会在提问前看到同意勾选，只发送**当次问题 + 上面那张表的聚合值**（可选：开启多轮后再带上本轮问答）。`daily_counts` 也只是 7 个整数，不含日期标签。

## 需要硬件组确认的四个问题

1. **`event_type` 口径**：是否维持 `1=使用动作 / 2=疑似无效 / 3=其他`？助手完全按这个口径分类，改口径要同步改三端。
2. **设备时间从哪来**：`timestamp=0` 的记录只能算"时间未知"，助手无法利用。校时流程直接决定这类记录的比例，也决定 `unknown_time` 提示出现的频率。
3. **自检测状态**（`HealthStatus` 特征，见 [`ai-continuation-task.md`](ai-continuation-task.md) 阶段 C2）：如果将来要展示设备健康，助手可以**解释**原因码，但不能**替代**底层规则判断。
4. **ACK/COMMIT 语义**：`last_sync_at` 应只在整轮同步成功后写入。否则助手会基于不完整的数据给出结论，并且 `stale_sync` 规则会误判。

## 不在范围内的（越界提醒）

下面三个听起来都很 user-friendly，但**不要做**：

| 想法 | 为什么不做 |
|---|---|
| 依从性评分 / 达标率 | 数据只代表设备被使用，**无法确认服药**；给分等于给出错误结论 |
| "该吃药了"定时提醒 | 属于医疗器械功能，项目文档明确禁止 |
| 剂量计算或调整建议 | 同上，且助手已禁止输出 |

助手侧已在提示词和规则里禁止上述内容，并有测试守卫（见 `mobile_app/test/assistant_rules_test.dart` 里的禁用词断言）。
