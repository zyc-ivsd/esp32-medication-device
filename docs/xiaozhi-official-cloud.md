# 小智官方云接入：可行性与下一步

> **2026-09-30 更新：小智路线（官方云 + 自建智控台）已整体放弃，本文仅作历史资料。** 在线助手的现行路线是 App 直连用户自己的模型（BYOK），API Key 只能是用户自己的、绝不出手机，见 [`assistant-model-access.md`](assistant-model-access.md)。下面的“可行性”“决策任务”“实施顺序”不再排期。

## 先看结论：三种“用小智”的方式

| 方式 | App 能用吗 | 说明 |
|---|---|---|
| **xiaozhi.me 官方云** | ❌ **不能** | 设备激活要求用 ESP32 eFuse 里的 HMAC KEY0 对服务器 challenge 签名，手机算不出来；官方也没有给第三方 App 的聊天 API。详见下文 |
| **自建 `xinnan-tech/xiaozhi-esp32-server` + 智控台** | ✅ **可以，仓库已支持** | 网关 `GATEWAY_MODE=xiaozhi` 走它的文字路径；**大模型、知识库/RAG、角色设定都在智控台里配**，步骤见 [`server/assistant-gateway/README.md`](../server/assistant-gateway/README.md) |
| 把 xiaozhi.me 上配好的模型/知识库拿来给自建服务端用 | ❌ 不能 | 配置存放在官方服务器上，两边不互通 |

**所以“在 xiaozhi.me 里配大模型和 RAG 然后给 App 用”做不到；但“在自建智控台里配，然后给 App 用”可以，而且已经实现。**

对齐时必须说清两点：

- **声纹识别对文字路径无效** —— 声纹需要麦克风音频，而 App 只发文字；
- 官方云那一条即使将来获准，也要先解决设备侧的 eFuse 激活，**不能靠让 App 输入 Token 绕过**。

## 目标

让其他 iGEM 队伍克隆公开仓库后，使用**各自**的小智官方账号完成可选的文字助手功能；不要求项目维护者长期运维一台服务器。Android 的本地记录、BLE、统计和 CSV 应继续在断网时可用。

## 核查到的官方接口边界

官方开源 ESP32 客户端公开的连接流程是“设备 OTA/激活配置 → 带设备身份与访问令牌的 WebSocket → hello 会话 → listen / TTS / Opus 消息”。官方文档的例子面向设备协议，并没有给出一个供通用 App 使用的公开 REST 聊天 API。见[官方 WebSocket 文档](https://github.com/78/xiaozhi-esp32/blob/main/docs/websocket_zh.md)和[官方项目 README](https://github.com/78/xiaozhi-esp32/blob/main/README_zh.md)。

官方固件从 OTA 配置使用 `Activation-Version`、`Device-Id`、`Client-Id` 等请求头，并提交板级系统信息；激活时，固件把 eFuse 用户数据中的序列号、服务器 challenge 和 HMAC-SHA256 响应交给 `/activate`，HMAC 由 ESP 芯片的 HMAC KEY0 计算。[官方 OTA 激活实现](https://github.com/78/xiaozhi-esp32/blob/main/main/ota.cc#L27-L67)、[官方挑战签名代码](https://github.com/78/xiaozhi-esp32/blob/main/main/ota.cc#L424-L492)。

这说明“App 填一个 WebSocket 地址或用户 Token”还不是完整方案。手机不能代表 ESP32 计算其 eFuse HMAC；不应把硬件密钥读出后传给 App。还需向小智官方确认：是否支持第三方 Android 客户端及专用设备注册/激活，有无公开且获准的移动客户端认证方式。**目前没有已验证的这种通用 App 凭据流程。**

当前硬件是 ESP32-C3 Arduino BLE 原型，现有协议只传时间文本；仓库中没有官方 OTA 注册、激活 challenge/HMAC、官方云 WebSocket 客户端。因此现有 0.3.0 APK 的在线助手连接的是上阶段自建 Python 网关；它不会直连 `xiaozhi.me` 或官方 WebSocket。自建网关目录可保留做研发/mock，不代表新目标已经实现。

## 交给组员的决策任务

| 负责人 | 要确认的问题 | 需要留下的证据 |
|---|---|---|
| 项目负责人 | 小智官方是否允许第三方 Android 应用以官方云账号为用户提供独立对话？官方推荐哪份客户端/激活规范？ | 官方文档或官方支持回复；注明日期和适用版本 |
| 硬件组 | 现有 ESP32-C3 模组、板子和固件是否具备官方激活要求的 Wi-Fi、稳定设备身份、序列号与安全 HMAC Key0？序列号/密钥是否已按官方方式烧录？ | 模组完整料号、芯片 eFuse 配置状态、Arduino 库/SDK 与功能检查；不要导出或共享密钥 |
| Android + 硬件组 | 如果官方要求真正的设备身份，是否支持保留 BLE 药品同步并增加设备侧 OTA/激活；或者需要更换官方支持的主控/整机固件？ | 复用现有设备、改造固件和换板三种方案的成本与可复现条件 |
| Android 成员 | 前述确认后，完成获官方支持的连接客户端、权限同意、错误恢复、令牌安全存储 | 用测试账号/设备验证激活、断线恢复、重新安装和账号隔离；保存脱敏步骤 |

## 实施顺序

1. **先向官方确认接口和设备注册政策。** 不要根据第三方逆向项目猜测 URL、HMAC 格式或共享测试令牌。
2. **硬件组检查模组和 eFuse provisioning。** 如缺少官方激活所需密钥或固件能力，先讨论正规烧录/官方支持板型；不要在真实设备上尝试未知烧录或写 eFuse，因为这类配置可能不可逆。
3. 用专用测试设备和测试账号走通官方提供的绑定流程，再检查是否能让 Android 作为该受支持客户端进行文字问答。官方设备 WebSocket 主要文档描述的是语音/音频流程；纯文字 `listen.detect.text` 是否受官方云的移动客户端策略支持，也要实测确认。
4. 只有确认官方云准许此客户端、能取得每个复现队伍自己的凭据且完成隐私评审之后，才为 Android 增加官方 Provider。访问令牌应经 Android Keystore 封装的安全存储，不写入 APK、源码、构建参数或 Wiki。
5. 给另一支队伍一套从零复现步骤：自己的官方账号、自己的兼容设备激活、安装 App、授权发送统计摘要。不得复用维护者的账号、序列号或令牌。
6. 如果官方不支持独立 Android 客户端，而硬件也不能按正规途径完成激活，就需要重新选路线：接受其他已有的官方支持客户端集成方式，或让团队评估自建/第三方后端。**没有官方支持的通用客户端接口时，不能承诺“无服务器又能稳定直连官方云”。**

## App 当前可以做和不能宣称的事

- 可以继续测试本地规则助手；它不依赖网络和账号。
- `server/assistant-gateway/` 是可运行实现，支持三种上游：`mock`（不调用模型）、`xiaozhi`（社区自建 `xinnan-tech/xiaozhi-esp32-server`）、`llm`（任意 OpenAI 兼容 API）。**三种都不是小智官方服务。**
- 不要把小智账号密码、开发板 HMAC 密钥、从未确认可分享的设备 Token 放到 App 输入框，也不要让所有参赛队共享一个测试身份。
- 在官方验证完成前，产品页和 Wiki 应写“官方云接入待确认/未实现”，不能写“已接入官方小智”。

## 最小验收

1. 另一队使用自己的官方账号和兼容设备，不借用本队服务器或秘密。
2. 激活/配对过程符合官方公开支持的步骤；重新安装或换手机后的归属行为已知。
3. 同意后只发送当次问题与说明过的统计摘要；拒绝时本地功能仍可用。
4. 官方真实文字回答到达 Android；断网、未配对、令牌失效时给出清楚错误，不伪装成本地/云端成功。
5. 把官方文档版本、App 版本、设备板型、账号步骤、测试限制记录在 Wiki，不留真实令牌、HMAC 或个人用药信息。
